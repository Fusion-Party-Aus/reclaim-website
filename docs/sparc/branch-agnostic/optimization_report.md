# SPARC Optimizer Report — Branch-Agnostic Modules

## Scope and method

Audit of `config/branch/*.mjs` against the Big O analysis in
[`architecture_blueprint.md`](./architecture_blueprint.md#6-big-o-analysis). This is a
structural complexity review; no runtime benchmarks were run. The intended branch count is at most
eight Australian states and territories.

## Findings

| Area                                                          | Structural complexity / basis                                                                                                                                                                                                                                                                                                                                                  | Assessment                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Resolver isolation (`resolver.mjs:186–250`)                   | For one resolution, scans the `B` manifest entries and, for each other branch, constructs a set from its `N` KV IDs and checks the current branch's KV IDs. This is `O(B·N)` plus `O(B)` scalar comparisons (more precisely, `O(B·N + B·N_current)` if current-branch namespaces are counted separately). The outer manifest validation is also `O(B)` (`manifest.mjs:86–99`). | This matches the blueprint's stated dominant resolver term. At `B ≤ 8`, and small KV lists, the scans are bounded and deterministic. No justified optimization.                                                                                                       |
| Theme token validation (`theme.mjs:80–127, 135–160, 168–219`) | `collectTokenErrors` is `O(R + T)` for one theme: required-role lookup, token-value validation, and unknown-token checks. `validateTokenContract` applies it to every manifest branch, so that exported operation is `O(B·(R + T))` in aggregate. `resolveTheme` validates only its selected theme, `O(R + T)`.                                                                | The blueprint's `O(T)` describes the single-theme case and suppresses the required-role term where `R ≤ T`. The all-manifest validator has a different aggregate bound; it does not create a problematic nested scan. No justified optimization at the current scale. |
| Provisioning singleton lookup (`provision.mjs:247–260`)       | `buildStarterContent` creates `K` documents, then each of `K` singleton types calls `.find()` across that list: `O(K²)` local work, plus `K` sequential `documentExists` calls and up to `K` sequential `createIfNotExists` calls. External request latency dominates the local lookup structurally, but was not measured.                                                     | The registry currently has four entries (`singletons.mjs:14`), so the repeated local scan is negligible. The sequential calls preserve a clear exists-then-create order and avoid introducing concurrency/race changes. No justified optimization.                    |
| `buildAllBranches` (`deploy.mjs:129–158`)                     | Performs `B` synchronous iterations. Each invokes resolution, whose manifest validation and isolation together make the config-validation work `O(B²·N + B·(T + S + C))` across the matrix, before callback build/verification work. Build costs are represented as `B·buildCost`; callbacks may add their own costs.                                                          | This is bounded by the small fixed branch count. The function itself does not promise asynchronous parallel builds, and parallelizing would alter failure/order behavior without evidence that it is needed. No justified optimization.                               |
| Leakage verification (`verify.mjs:175–210`)                   | For one branch, serializes a non-string output once (`O(O)` time and allocation), then checks a fixed set of up to six foreign tokens for each of `B−1` branches using `String.includes`: `O(B·O)` scan work in the worst case. Running it once per branch in the matrix gives `O(B²·O)`.                                                                                      | This matches the blueprint's bound. The number of patterns is fixed and `B ≤ 8`; a multi-pattern algorithm would add complexity without a demonstrated benefit. No justified optimization.                                                                            |

## Recommendations

**No source changes are recommended.** The identified repeated scans and quadratic matrix terms are structurally real, but branch count, token/KV counts, singleton count, and the number of leakage patterns are all small and bounded for the stated use. No measurements indicate that these operations are material, and there is no basis for changing ordering, concurrency, or scan strategy.

No runtime performance claims are made in this report.
